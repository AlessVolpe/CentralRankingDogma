# Milestone 3.1.3: External integration contract and JSON CLI

**Status:** Implementation in progress. PR A merged the versioned contract,
schemas and fixture validators. PR B supplies the native `validate`, `generate`
and `resolve` transport implementation, pending repository CI and review.
Monte Carlo transport, progress and cancellation belong to PR C; Linux Docker
packaging and the independent Python consumer belong to PR D.

## Objective and system boundary

Complete the last planned native integration milestone before implementation
of the separate Python web application. The future Python service will own
team registration, database persistence, authorized original-calendar imports,
job orchestration and decimal score display. An installed `leaderboard-json`
executable will accept one versioned JSON request over stdin and return one
versioned JSON response over stdout. The ISO C11 library owns validated
competition snapshots, transient calendar generation, season resolution,
ranking and Monte Carlo. No Python, HTTP, JSON parser or database dependency
is added to the installed `Leaderboard::leaderboard` library.

The [JSON CLI v1 contract](../integration/json-cli-v1.md) is normative for this
milestone. [Request](../../schemas/leaderboard-cli-v1-request.schema.json),
[response](../../schemas/leaderboard-cli-v1-response.schema.json) and
[progress](../../schemas/leaderboard-cli-v1-progress.schema.json) schemas,
plus versioned examples, define its wire representation and failure cases.

## Scientific and architectural invariants

- External identities are RFC 9562-layout UUID strings. Python creates them;
  `competition_t` sorts and deep-copies the source data independently.
- Fantasy scores and configurable match thresholds are integer **tenths**:
  JSON `665` represents a displayed score of `66.5`. `PENDING` scores are
  explicitly represented as zero with pending status, never inferred as final.
- A complete original fixture list and team-by-round score matrix form the
  immutable snapshot. Alternative schedules do not mutate either.
- The original calendar can be resolved even if it fails the stronger
  one-factorization contract required by calendar generation.
- `FINALIZED_PREFIX` is provisional. `FULL_SEASON` rejects pending scores.
- Generated calendars are transient: preview and generation/resolve happen
  in one process, or deterministic replay regenerates by seed and ordinal
  with a matching engine identifier. No calendar storage/import API.
- Heapsort remains the default; AVL is an opt-in backend and must return
  equivalent sporting results, including shared competition ranks.
- Statistics are separated into `basic` and `advanced` response namespaces;
  advanced diagnostics do not imply uniform sampler probabilities or
  statistical inference absent from the native implementation.

The native JSON executable is intentionally distinct from the current
educational `leaderboard_cli` target. The transport implementation may vendor
a permissively licensed JSON parser into the executable only; license and
upstream revision must be documented. Avoid a new dependency in public headers.

## Verification and test matrix

- Draft 2020-12 schema checks for `validate`, `generate`, `resolve`, `simulate`,
  success/failure envelopes and progress events; all unknown keys rejected.
- Semantic validation: duplicate JSON object keys, invalid Unicode, UTF-8
  limits, duplicate UUIDs/matchdays/scores, missing matrix cells, invalid
  home/away schedules, score status and unsigned overflow.
- Calendar constraints: original snapshot valid but not generator-compatible;
  deterministic replay using identical engine ID, seed and sample index;
  mismatched engine ID rejected; generated fixtures are not persisted.
- Season resolution: full versus finalized-prefix, default and custom rules,
  home advantage, exact shared ranks, UUID ordering, both ranking backends.
- Simulation: independent and chain generation, exact accepted/attempt counts,
  no false uniformity claims, accepted partial completion states, cancellation,
  stdout/error stream isolation, CSV cleanup, and bounded resources.
- Platform scope: native Linux and Windows regression checks; packaged Linux
  Docker execution; Python `subprocess` integration and timeout handling.

All numbers in future JSON result fixtures must be asserted against actual
C API results before those fixtures are treated as executable golden vectors.
PR A examples only demonstrate transport shape and schema conformance.

## Compatibility and follow-up

The public C11 API, GPL-3.0-only licensing, original fixture import and
3.1.2 scientific findings remain unchanged. Schema version `1.0` is independent
of the native package version; PR B deliberately does not bump CMake's 3.1.2
development number. `simulate`, progress, cancellation and CSV exports are not
implemented by PR B. The parser and serializer are separate private C11 code,
not a dependency of the installed `Leaderboard::leaderboard` library.

PR B's native black-box CTest must pass against the actual linked C library;
compile-only and stub-based smoke checks are not acceptance evidence. PR D
will add installed executable packaging and Docker Linux verification.

The web application begins after PR D's accepted integration round trip and
remains a separate project. See the [roadmap](../roadmap.md),
[system boundary](../architecture/system.md) and
[research limitations](../research/limitations.md).

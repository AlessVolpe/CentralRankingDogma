# Milestone 3.1.2: Ranking integration and scientific evaluation

**Status:** Implemented and empirically evaluated in PR #23.
PR A introduced the optional composite-key ranking backend. PR B implements
benchmark, memory and statistical-analysis tooling, and has completed a
**scoped synthetic evaluation** with verified primary artifacts. See the
[measured results](../research/results-3.1.2.md) for source revision, evidence
hashes, observed performance, uncertainty, and explicit research limitations.

## Objective

Integrate the existing hashmap/BOSTree `ranking_t` infrastructure into the
Fantacalcio season resolver as an **optional, mathematically equivalent ranking
backend**, then measure ranking efficiency and sporting-outcome sensitivity
under reproducible, controlled Monte Carlo experiments. Complete this milestone
through **two distinct PRs**: implementation first, evaluation second.

## Scientific or architectural contribution

The 3.1.1 `season_resolve()` interface still defaults to the in-place
heapsort. PR A adds `season_resolve_with_options()` with a selectable AVL
backend. The generic `ranking_t` continues to support its original signed
`int64_t` score plus string-ID order, and now supports fixed-size owned keys
with a borrowed comparator context. Fantacalcio sporting keys are compared
lexicographically by the resolver adapter, not by scalar packing.

The sporting key remains lexicographic descending:

```math
K_i=(P_i,F_i,\mathrm{GD}_i),
```

where `P_i` is championship points, `F_i` is the sum of FINAL fantasy-score
tenths over evaluated rounds, and `GD_i` is goal difference. Equal keys share
standard competition ranks (e.g. `1,1,3`); UUID ordering is **presentation
only**, never an invented sporting tiebreaker. Composite ordering must not be
implemented through lossy or overflow-prone packing into a single `int64_t`.

The scientific comparisons address two separate questions: the performance of
constructing and querying a completed ranking, and the costs of maintaining a
ranking under a sequence of incremental standings changes. Small leagues need
not favor a tree over a contiguous array; measured outcomes, including a
heapsort advantage, are valid results.

## Deliverables and implementation evidence

### PR A: Composite ranking integration (implementation prerequisite)

- Extend `ranking_t` with `ranking_new_custom`, `ranking_upsert_key`,
  `ranking_get_key` and `ranking_at_key`. Copied fixed-size keys and a borrowed
  callback context preserve the existing scalar API and failure guarantees.
- Implement a Fantacalcio adapter that maps team UUID identity and
  `(championship_points, fantasy_total_tenths, goal_difference)` into the new
  ordering, with **separate sporting-tie classification**.
- Introduce `season_resolution_options_t` and `season_resolve_with_options()`;
  keep `season_resolve()` as a heapsort compatibility wrapper.
- Append `ranking_backend` to `monte_carlo_options_t`, defaulting to
  `SEASON_RANKING_HEAPSORT`; apply the same selection to baseline and draws.
- Add differential tests for every ranked field, UUID presentation order,
  all-equal keys, exact sporting ties, skipped ranks, extreme representable
  values, insertion/update order, and full/finalized-prefix calendar results.
- Add allocation-failure and rollback tests for the tree-backed path;
  verify no partial results or corrupted source state escape on failure.

**PR A acceptance gate:** both backends return identical rank entries and
sporting ranks for the same snapshot, scoring rules, evaluated scope and
calendar. New CTests, fault-injection tests, installed-consumer smoke, Linux
and Windows CI must pass on the PR before its implementation is considered
verified. No runtime advantage is assumed or claimed.

### PR B: Controlled scientific evaluation (depends on PR A)

- Compare completed-ranking construction, selection and query costs for the
  array/heapsort and hashmap/BOSTree implementations using identical inputs.
- Compare incremental insert/update/delete and rank-query sequences against a
  clearly defined array-based baseline with identical observable semantics.
- Record separate timing and allocation/memory costs for calendar generation,
  match resolution, ranking and aggregation. Do not benchmark a whole Monte
  Carlo run against an isolated tree operation.
- Use league-sized tests (commonly 8, 10 or 12 teams) and larger synthetic
  **ranking-only** workloads; do not present synthetic team counts as valid
  Serie A competition configurations.
- Run reproducible independently seeded batches with recorded seeds, options,
  sample counts, compiler/build settings, hardware and code revision. Analyze
  observed schedule-fingerprint diversity, reported acceptance, outcome
  sensitivity and seed-level uncertainty. **Chain dependence and sampler
  comparisons remain deferred:** no chain-mode measurements or uniformity
  claims are included in the accepted 3.1.2 experimental scope.
- Publish benchmark procedures, machine-readable results, statistical
  interpretation and limitations in the scientific documentation. Treat
  `leaderboard_bench` from 3.0.10 as existing infrastructure, not evidence of
  an already completed 3.1.2 comparison.

**PR B acceptance gate:** independent reference checks support every reported
ranking result; experiments are rerunnable from recorded configurations;
performance differences are measured with variability and limitations; and
no assumption of uniform calendar sampling or independent chain draws is
silently introduced.

## Verification and limitations

Both PRs require GCC/Clang C11 regression tests, Windows UCRT64 and Linux
CI, installed public-consumer checks, sanitizer checks where supported, and
scientific documentation validation. PR A requires exact differential tests
and failure-injection coverage; PR B requires controlled workload equivalence
and reproducible benchmark artifacts. Claim no implementation evidence before
the relevant changes merge and their checks complete.

An order-statistics tree provides logarithmic positional operations, but is
not necessarily the fastest choice for 8-12 teams; allocations, cache locality
and repeated rebuilds must be measured. The calendar generator remains
unproven uniform; chain samples may be correlated; fixed historical team
performance is a counterfactual assumption rather than a causal prediction.

## Scientific acceptance record (2026-11-18)

- Clean experiment source revision: `f5ac3699a0715f033720a9aab7ff7c706393950d`.
- Strict evidence validation: seven ranking sizes, 2,520 rows, 30 paired
  heapsort/AVL league/seed configurations, 16 Massif profiles; 263/263 primary
  artifacts passed hash verification.
- Synthetic sampling: 8, 10 and 12 teams, one round-robin period each;
  `recombine` + `independent`; 10 seeds and 1,000 calendars per seed.
- Verified outcomes: exact backend observation equality; batch construction
  favors heapsort, while AVL favors larger incremental updates at a memory
  cost. Results and interpretation appear in
  [results-3.1.2.md](../research/results-3.1.2.md).
- **Explicitly deferred:** chain/shuffle-mode analysis, common string-ID query
  comparison, multi-period/historical league inference, and uniform-calendar
  representativeness. These are not claimed as completed findings.

## Compatibility and follow-up

Preserve 3.1.0/3.1.1 default behavior and keep `ranking_t` domain-neutral.
The PR A implementation adds a **solid** resolver-to-ranking arrow in the
README because the selectable dependency now exists. `ranking_t` maintains
zero-based individual positions; the resolver still assigns shared 1-based
sporting ranks. Public headers and ownership remain C11-compatible.
The native CMake project version is 3.1.2. Its verified evidence and the
limitations of the scoped scientific evaluation are recorded in the
[published result](../research/results-3.1.2.md). Release publication and
merge of PR #23 remain distinct from implementation and evidence acceptance.

The next native milestone is [3.1.3](3.1.3.md): external input/output contracts
and JSON serialization. The Python application and its database, registration,
fixture import and UI belong to a separate project and are not part of 3.1.2.
See the [roadmap](../roadmap.md), [ranking reference](../reference/ranking.md),
[season-resolution reference](../reference/season-resolution.md),
[research methodology](../research/methodology.md) and
[performance plan](../research/performance.md).
